# Provider adapter and verification limits

The pilot works without an LLM API. The current authorized budget is hard-coded at EUR 0. `authorize(Action.MODEL)` denies a request before it reads a key or opens a connection. `MONTHLY_BUDGET_EUR`, `MAX_LLM_CALLS_PER_RUN` and other environment values cannot grant spending authority. A future owner-approved budget change needs a separately reviewed enforcement implementation with persistent reservations, monthly accounting and a worst-case request allowance, not just a new environment value.

The prepared adapter is `ai_ceo.worker.query_model`. Its protocol is a JSON request to `AI_API_BASE_URL` plus `/chat/completions`, with `AI_MODEL`, a bearer key from `AI_API_KEY`, system and data messages, a maximum of 2,000 output tokens, a 30-second request timeout, and a 400,000-byte response cap. The hostname must exactly match `AI_ALLOWED_HOST`. Redirects and URLs with credentials are rejected. It expects a string in `choices[0].message.content` containing the decision object, then applies the source/schema validator. It cannot execute tools or generated code. External content is data, not authority.

For a provider with a different API, implement a narrow adapter with the same `entries -> decision object` contract. Put the permission and request-count checks before transport, fix the allowed endpoint host, keep TLS verification enabled, bound input/output/time, redact errors, and validate the returned decision against the supplied source URLs. Never import or execute model-supplied adapter code or an arbitrary module selected by external text. Test request and response contracts with synthetic data before considering a live call. A provider advertised as "free" still requires verification of actual account/usage limits under the spending policy.

The existing adapter is covered by no-request budget tests, but no live endpoint, authentication, model capability, provider price or alternative adapter has been verified. No JEV compatibility is assumed. Do not describe a mocked result or a configurable URL as a working provider integration.

Provider keys belong in environment variables or a deployment secret manager. The application does not load `.env` automatically and must never log keys, webhook secrets, raw payment payloads or banking identifiers. `ALERT_WEBHOOK_URL` is a reserved unused example setting; notifications remain blocked.
